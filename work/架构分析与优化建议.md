# EasyChat Electron IM 项目架构分析与优化建议

---

## 项目概述

本项目是一款基于 **Electron + Vue 3 + Vite** 技术栈构建的桌面端即时通讯（IM）应用，项目名称为 EasyChat。核心技术选型如下：

| 技术领域 | 技术选型 | 说明 |
|---------|---------|------|
| 桌面框架 | Electron | 跨平台桌面应用载体 |
| 前端框架 | Vue 3 (Composition API) | 渲染层 UI 框架 |
| 构建工具 | Vite (electron-vite) | 开发/构建工具链 |
| 状态管理 | Pinia + pinia-plugin-persistedstate | 响应式状态管理 + 持久化 |
| UI 组件库 | Element Plus | 基础 UI 组件 |
| 本地数据库 | better-sqlite3 | 主进程 SQLite 数据库 |
| 富文本编辑 | tiptap | 笔记编辑器 |
| 文件处理 | piscina (Worker Threads) | 多线程文件分片计算 |
| HTTP 客户端 | Axios | 渲染进程 HTTP 请求 |
| 实时通信 | WebSocket (自定义二进制协议) | 主进程 WS 长连接 |
| 本地存储 | electron-store | Token/用户信息持久化 |
| 跨窗口事件 | 自定义 eventEmitter + piniaShareApi | 多窗口状态同步 |

项目采用 Electron 经典的多进程架构：

- **主进程 (Main Process)**：负责数据库操作、IPC 通信、文件传输、WebSocket 管理、窗口管理
- **渲染进程 (Renderer Process)**：负责 UI 渲染、状态管理、用户交互
- **预加载脚本 (Preload)**：作为主进程与渲染进程的安全桥梁，通过 contextBridge 暴露 API

本地数据库包含 5 张核心表：`message`（消息）、`conversation`（会话）、`friend_relation`（好友关系）、`device_user_record`（设备登录记录）、`favorites`（收藏/笔记）。

## 架构优势

### 1. 数据库访问层设计合理

项目采用了清晰的数据库分层架构：

- **`src/main/DB/mainDB.js`**：核心数据库引擎，封装了 `queryAll`、`insert`、`update`、`deletes`、`multipleInsert` 等通用方法，使用 `globalColumnsMap` 实现了数据库字段名与驼峰命名的自动映射。
- **`src/main/DB/select.js`、`insert.js`、`update.js`、`delete.js`**：按 CRUD 职责拆分，各司其职。
- **`src/renderer/src/db/dualDB.js`**：渲染进程的数据库代理层，统一封装了所有本地数据库操作。
- **`src/renderer/src/db/syncDB.js`**：双写同步层，同时操作本地数据库和远程服务端。

这种分层使得数据库操作逻辑清晰，便于维护。

### 2. WebSocket 协议设计专业

`src/main/websocket.js` 中的 `WebSocketManager` 类实现了自定义二进制协议，包含完整的消息帧结构：

```
| 魔数 (4B) | 版本号 (1B) | 序列化方式 (1B) | 消息类型 (1B) | 序列号 (4B) | 填充 (1B) | 正文长度 (4B) | 正文 (变长) |
```

同时实现了心跳保活（60秒间隔）、断线重连（最大3次）、消息路由分发等核心能力。

### 3. 文件传输引擎设计精良

`src/main/File/` 目录下的文件传输系统设计尤为出色：

- **Worker 线程分片**（`createWorkerProcess.js`）：使用 piscina 线程池进行文件分片哈希计算，避免阻塞主进程。
- **背压控制**（`fileUpload.js`）：通过 `MAX_UPLOAD_BACKLOG` 阈值和 `backpressurePausedFileSet` 实现了读流与上传速度的自适应平衡。
- **消息队列**（`src/main/Util/messageQueue.js`）：自研的可控并发 + 限流任务队列，支持暂停/恢复/清除/空闲等待，设计完备。
- **断点续传**：通过 `checkUploaded` 接口检查已上传分块，支持续传。

### 4. 消息 ACK 与超时机制

`src/renderer/src/stores/modules/MessageStore.ts` 中实现了完整的消息可靠性保障：

- `pendingMessages` (Map) 跟踪发送中的消息
- `startTimeoutChecker` 每秒轮询检查超时（5秒阈值）
- `onReceiveAck` 处理服务端确认
- `onReceiveError` 处理服务端错误
- 消息状态三态：0=发送中、1=发送成功、2=发送失败

### 5. 组件设计亮点

- **`ContextMenu.vue`**：基于 Teleport + 自定义 Hook (`useContextMenu.js`) 的右键菜单组件，解耦良好，可复用性强。
- **`MessageContentManage.vue`**：基于渲染函数 (`h()`) 的消息内容分发组件，通过 `msgType` 动态渲染不同类型的消息子组件，策略模式运用得当。
- **通知组件系列**（`FriendAddNotify.vue`、`GroupAddNotify.vue` 等）：统一的通知展示组件，职责单一。

### 6. 多窗口状态同步方案

`src/renderer/src/stores/plugins/shareStorePlugin.ts` 实现了 Pinia 跨窗口状态同步插件，通过 IPC 广播机制让多个窗口的 Store 保持同步。`eventEmitter.js` 进一步封装了基于此机制的跨窗口事件总线。

## 优化空间分析（按优先级排序）

### P0 - 安全风险

#### 1. Electron 安全配置存在严重隐患

**问题文件**：`src/main/index.js` (第 69-79 行)

```javascript
webPreferences: {
    webSecurity: false,        // 关闭了同源策略保护
    nodeIntegration: true,     // 允许渲染进程访问 Node.js API
    contextIsolation: true,
    preload: join(__dirname, '../preload/index.js'),
    sandbox: false             // 禁用了沙箱模式
}
```

`webSecurity: false` 配合 `nodeIntegration: true` 和 `sandbox: false`，构成了严重的安全风险组合。一旦渲染进程加载了恶意内容（如 XSS 攻击），攻击者可直接访问 Node.js API，执行任意系统命令。

**同样的配置出现在** `src/main/Util/createNewWindow.js` (第 67-75 行)，所有子窗口继承了相同的安全风险。

**优化建议**：
- 将 `nodeIntegration` 设为 `false`
- 将 `sandbox` 设为 `true`
- 移除 `webSecurity: false`，通过正确配置 CORS 或使用自定义协议解决跨域问题
- 使用自定义协议 (`registerFileProtocol` 或 `registerStreamProtocol`) 加载本地资源

#### 2. IPC 通信安全边界模糊

**问题文件**：`src/preload/index.js`

当前 preload 暴露了 **9 个全局 API 对象**，共计约 50+ 个方法。部分设计存在问题：

**(a) send 与 invoke 混用导致可靠性问题**

```javascript
// 使用 send - 无返回值，无法确认操作是否成功
updateDBData: () => { ipcRenderer.send('update:db') },
saveSentMessage: (message) => { ipcRenderer.send('save:message', message) },
deleteMessage: (conversationId, messageId) => { ipcRenderer.send('delete:message', conversationId, messageId) },

// 使用 invoke - 有返回值，可以确认操作结果
queryConversationList: () => { return ipcRenderer.invoke('query:conversation') },
```

写操作（`save`、`update`、`delete`）使用 `send` 而非 `invoke`，渲染进程无法感知操作是否成功，数据库写入失败时 UI 层无法做出响应。

**(b) 部分 IPC 监听器未清理**

```javascript
// preload/index.js 第 119-135 行
updateUploadProgress: (callback) => {
    ipcRenderer.on('upload-progress', callback)   // 只注册，无对应 removeListener
},
updateUploadStatus: (callback) => {
    ipcRenderer.on('upload-loadStatus', callback)  // 同上
},
updateDownloadProgress: (callback) => {
    ipcRenderer.on('download-progress', callback)   // 同上
}
```

每次调用这些方法都会新增一个监听器，但从代码中看不到对应的 `removeListener` 或 `removeAllListeners` 调用，存在内存泄漏风险。

**(c) 非隔离安全的回调注册**

```javascript
// preload/index.js 第 182-184 行
getCapturePngBuffer: (channel, func) => {
    ipcRenderer.on('window:get-capture-pngBuffer', (event, ...args) => {
        func(...args)
    })
}
```

渲染进程可以传入任意 channel 名称注册监听器，未做白名单校验。

**优化建议**：
- 将所有数据库写操作改为 `invoke`，确保渲染进程可以获取操作结果
- 为所有 `ipcRenderer.on` 提供配套的 `removeListener` 方法
- 使用 `ipcRenderer.once` 替代不需要多次触发的监听
- 在 preload 中对 channel 名称进行白名单校验

### P1 - 架构设计问题

#### 3. 数据库层 SQL 拼接方式存在注入风险

**问题文件**：`src/main/DB/mainDB.js`

虽然当前数据主要来自内部 IPC 调用，但 `mainDB.js` 中的 SQL 拼接方式仍值得关注：

```javascript
// mainDB.js 第 129 行 - multipleInsert
const sql = `${insertPrefix} into ${tableName} (${tableFieldNames.join(",")}) values ${batchPlaceholder}`

// mainDB.js 第 154 行 - insert
const sql = `insert into ${tableName} (${tableFieldNames.join(',')}) values (${placeholder})`

// mainDB.js 第 192 行 - update
const sql = `update ${tableName} set ${dataPlaceholder} where ${conditionPlaceholder}`
```

`tableName` 直接拼接到 SQL 中，虽然当前由 `globalColumnsMap` 做了间接校验（只有存在于映射中的表名才能通过），但字段值均使用了参数化查询（`?` 占位符），这一点是好的。

**真正的风险在于**：`multipleInsert` 的 `insertPrefix` 参数来自调用方，如果传入非预期值（如 `INSERT OR REPLACE`），可能产生非预期行为。

**优化建议**：
- 对 `tableName` 和 `insertPrefix` 增加白名单校验
- 将 `insertPrefix` 改为枚举类型，限制可选值
- 考虑引入轻量级 ORM 或 Query Builder（如 `knex`），统一 SQL 构建方式

#### 4. 渲染进程直接通过 `window.xxx` 全局对象访问 IPC API

**问题文件**：`src/renderer/src/db/dualDB.js`、`src/renderer/src/stores/plugins/shareStorePlugin.ts` 等

```javascript
// dualDB.js - 大量直接使用 window.dbApi
const conversationList = await window.dbApi.queryConversationList()
await window.dbApi.saveSentMessage(message)

// shareStorePlugin.ts
(window as any).piniaShareApi.setStoreInfo(...)
(window as any).piniaShareApi.sendStoreInfo(...)

// MessageStore.ts 第 78 行
;(window as any).wsApi.sendMessage(wsType, 0, payload)
```

整个渲染进程中大量使用 `(window as any).xxxApi` 模式访问 preload 暴露的 API，存在以下问题：

1. **类型不安全**：TypeScript 无法推断 `window` 上的自定义属性类型
2. **缺乏封装**：组件直接依赖全局变量，难以测试和替换
3. **命名空间污染**：9 个全局对象挂载在 `window` 上

**优化建议**：
- 创建统一的 `src/renderer/src/services/ipc.ts` 封装层，提供带类型定义的 API 访问
- 通过 Vue 的 `provide/inject` 机制注入 IPC 服务
- 声明全局类型定义文件 `src/renderer/src/types/electron.d.ts`

```typescript
// 示例：src/renderer/src/types/electron.d.ts
interface DbApi {
  queryConversationList(): Promise<Conversation[]>
  queryFriendList(): Promise<Friend[]>
  loadMessage(conversationId: string, pageInfo: MessagePageInfo): Promise<MessagePageResult>
  // ... 其他方法
}

interface Window {
  dbApi: DbApi
  wsApi: WsApi
  // ... 其他 API
}
```

#### 5. 路由守卫过于简单

**问题文件**：`src/renderer/src/router/router.js` (第 208-231 行)

```javascript
router.beforeEach(async (to, from, next) => {
  // 仅对两个路由做了特殊放行
  if (to.path === '/friendAdd' || to.path === '/createGroup') {
    next()
    return
  }

  const token = await window.userInfoApi.storeGetUserInfo('token')

  if (to.path === '/') {
    if (token) {
      next('/pendingLogin')
    } else {
      next('/login')
    }
    return
  }
  // 其他所有页面直接放行
  next()
})
```

当前路由守卫存在的问题：

1. **仅对根路径做了 token 判断**：其他所有路由（`/main`、`/chat`、`/setting` 等）均直接放行，未登录用户可通过 URL 直接访问
2. **路由缺少 meta 信息**：没有定义路由元数据（如 `requiresAuth`、`layout` 等），无法做精细化权限控制
3. **没有路由懒加载**：所有页面组件在文件顶部全部同步导入，增大打包体积

**优化建议**：
- 为需要认证的路由添加 `meta: { requiresAuth: true }`
- 在全局守卫中统一拦截未认证的访问
- 使用路由懒加载 (`() => import(...)`) 实现代码分割
- 增加路由级别的加载状态和错误处理

```javascript
// 优化示例
{
  path: '/main',
  component: () => import('../views/layout/Main.vue'),
  meta: { requiresAuth: true },
  children: [
    {
      path: '/chat',
      component: () => import('../views/chat/Chat.vue'),
      meta: { requiresAuth: true, layout: 'main' }
    }
  ]
}
```

#### 6. 窗口管理不够健壮

**问题文件**：`src/main/Util/createNewWindow.js`、`src/main/IPC/chatToolIPC.js`

**(a) 窗口重复关闭/销毁问题**

`chatToolIPC.js` 中存在对同一窗口的多次关闭操作：

```javascript
// chatToolIPC.js 第 37-39 行 (第一次关闭)
windowPool.delete('capture')
captureWindow.close()

// chatToolIPC.js 第 69-70 行 (第二次关闭 - 重复!)
windowPool.delete('capture')
captureWindow.close()
```

在 `window:save-capture` 处理函数中，截屏窗口被关闭了两次，第二次调用时 `captureWindow` 可能已被销毁，将导致运行时错误。

**(b) 窗口池缺少生命周期管理**

```javascript
// createNewWindow.js
const windowPool = new Map()

// 仅在 closed 事件中清理
window.on('closed', () => {
    windowPool.delete(windowType)
})
```

窗口池只做了基本的添加和 `closed` 事件清理，缺少：
- 窗口超时管理（防止僵尸窗口）
- 窗口状态查询接口
- 批量销毁能力
- `createExtraWindow` 中窗口已存在时直接返回 `undefined`，调用方无法获取已存在的窗口实例

**优化建议**：
- 修复 `chatToolIPC.js` 中的重复关闭问题
- 将 `createExtraWindow` 改为"获取或创建"语义，窗口已存在时返回现有实例
- 增加窗口健康检查和超时销毁机制
- 在应用退出时统一销毁所有子窗口

### P2 - 代码质量问题

#### 7. 大量 `(window as any)` 类型断言

**涉及文件**：多个 `.ts` 和 `.vue` 文件

```typescript
// shareStorePlugin.ts
(window as any).piniaShareApi.setStoreInfo(...)
(window as any).piniaShareApi.sendStoreInfo(...)

// MessageStore.ts 第 78 行
;(window as any).wsApi.sendMessage(wsType, 0, payload)
```

项目中存在大量 `(window as any)` 类型断言，绕过了 TypeScript 的类型检查系统。这不仅使类型推断失效，还隐藏了潜在的运行时错误。

**优化建议**：
- 创建 `electron.d.ts` 全局类型声明文件
- 为所有 preload API 定义完整的 TypeScript 接口
- 消除所有 `(window as any)` 断言

#### 8. TypeScript 严格模式缺失

项目采用了 `.ts` 文件编写 Pinia Store 和类型定义，但从代码风格来看，缺少 TypeScript 严格模式的约束：

- `MessageStore.ts` 中 `fileMessgaeMap`（拼写错误：应为 `fileMessageMap`）的类型定义不够严谨
- `pendingMessages` 使用 `new Map()` 但未在 state 类型中标注泛型
- `timeoutTimer` 的类型标注为 `NodeJS.Timeout | null`，但在渲染进程中应使用 `number | null`（`setInterval` 返回 number）

**优化建议**：
- 在 `tsconfig.json` 中开启 `"strict": true`
- 修复类型错误和拼写错误
- 为所有 Store 的 state 提供完整的类型标注

#### 9. 错误处理缺乏统一机制

**涉及文件**：几乎所有模块

当前项目的错误处理方式高度不统一：

```javascript
// mainDB.js - 数据库操作错误仅 console.error
const run = (sql, params) => {
    try {
        const stmt = db.prepare(sql)
        const result = stmt.run(params)
        return result.changes;
    } catch (err) {
        console.error('操作数据库失败', err)  // 无返回值，调用方无法判断是否成功
    }
}

// websocket.js - WS 解析错误仅 console.warn
} catch (e) {
    console.warn('消息解析失败', e)
}

// fileUpload.js - 上传失败仅 console.log
}).catch(() => {
    console.log('文件上传失败')
})

// request.js - 401 以外的错误直接跳登录页
} else {
    console.error('其他错误', error)
    window.api.resizeWindow('login')
    window.location.href = '#/login'
}
```

问题汇总：
1. 部分 `catch` 只打印日志，不上报也不通知用户
2. `request.js` 中非 401 错误直接跳登录页，过于粗暴
3. 数据库操作失败时 `run()` 返回 `undefined`，调用方无法感知
4. 缺少全局错误边界和未捕获异常处理

**优化建议**：
- 建立统一的错误处理层级：
  - **底层**（DB/网络）：抛出带错误码的自定义错误
  - **中间层**（IPC/Store）：捕获错误并转换为 UI 可消费的状态
  - **顶层**（组件）：通过 Notification/Toast 向用户展示
- 在 `src/main/index.js` 中添加 `process.on('uncaughtException')` 和 `process.on('unhandledRejection')`
- 在渲染进程添加 `app.config.errorHandler` 全局错误处理
- `request.js` 的错误拦截器应按 HTTP 状态码分级处理

#### 10. 样式架构不统一

**涉及文件**：`src/renderer/src/css/layout.css`、各 `.vue` 组件

项目中样式存在明显的不一致：

**(a) 颜色值硬编码与 CSS 变量混用**

```css
/* layout.css - 使用 rgba 硬编码 */
background-color: rgba(35, 45, 60, 0.2);
border-right: 1px solid rgba(66, 153, 225, 0.4);

/* ContextMenu.vue - 完全不同的颜色体系 */
background: rgba(255, 255, 255, 0.9);
color: #1d1d1f;
```

`layout.css` 使用深色科技风格（`rgba(35, 45, 60, ...)`），而 `ContextMenu.vue` 使用浅色背景（`rgba(255, 255, 255, 0.9)`），视觉风格不统一。

**(b) 样式组织方式不一致**

- 部分样式放在全局 CSS 文件（`layout.css`、`account.css`）
- 部分使用 `<style scoped>` 内联在组件中
- 部分使用 `:deep()` 穿透 Element Plus 组件样式

**优化建议**：
- 建立 CSS 变量体系，在 `:root` 或主题文件中定义设计令牌 (Design Tokens)
- 统一颜色主题（深色/浅色），所有组件引用 CSS 变量而非硬编码值
- 建立 BEM 或类似的命名规范，统一管理全局样式

```css
/* 示例：统一的设计令牌 */
:root {
  --color-bg-primary: rgba(35, 45, 60, 0.2);
  --color-bg-secondary: rgba(40, 50, 65, 0.2);
  --color-border: rgba(66, 153, 225, 0.4);
  --color-text-primary: #f0f0f0;

  --color-accent: rgba(66, 153, 225, 1);
  --radius-sm: 4px;
  --radius-md: 6px;
  --radius-lg: 8px;
```

### P3 - 架构优化方向

#### 11. 收藏/笔记表设计混合存储

**问题文件**：`src/main/DB/tableInfo.js` (第 79-90 行)

```sql
CREATE TABLE IF NOT EXISTS favorites (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id TEXT NOT NULL,
    title TEXT,
    content TEXT NOT NULL,
    source_username TEXT,
    type INTEGER NOT NULL DEFAULT 0,   -- 类型区分不够清晰
    created_at INTEGER NOT NULL DEFAULT (strftime('%s', 'now') * 1000),
    updated_at INTEGER NOT NULL DEFAULT (strftime('%s', 'now') * 1000)
);
```

`favorites` 表同时存储"笔记"和"收藏消息"两种不同语义的数据，仅靠 `type` 字段（`INTEGER DEFAULT 0`）区分。问题包括：

1. `type` 字段缺少枚举定义，`0` 代表什么、`1` 代表什么不明确
2. 笔记有 `title`，收藏消息可能没有，但 `title` 字段对两者都可用
3. 收藏消息应关联原始消息的 `message_id`，但表中无此字段
4. `content` 字段对笔记存储富文本，对收藏消息存储什么语义不清

**优化建议**：
- 明确 `type` 字段的枚举定义，并在 `constants.js` 中添加常量
- 考虑拆分为 `notes`（笔记）和 `favorites`（收藏）两张表
- 如保留单表，增加 `source_message_id` 字段关联原始消息

#### 12. 双写同步层缺乏事务保障

**问题文件**：`src/renderer/src/db/syncDB.js`

```javascript
// syncDB.js - 本地和远程操作没有事务保障
const updateConversationTopStatus = (conversationId, userId, status) => {
    // 更新本地数据库
    updateConversation(condition, data)    // 操作 A
    // 更新服务端
    updateConversationTopStatusApi(conversationId, status)  // 操作 B
}
```

本地操作和服务端操作是独立的，如果操作 B 失败（网络异常），本地数据已经修改，导致数据不一致。

**优化建议**：
- 实现乐观更新策略：先更新 UI，再同步服务端，失败时回滚
- 或实现最终一致性：本地操作标记为"待同步"，后台定期重试
- 至少应对服务端操作失败的情况做日志记录和用户提示

#### 13. Pinia 持久化缓存策略存在边界问题

**问题文件**：`src/renderer/src/stores/modules/ConversationStore.ts`、`ContactListStore.ts`

```typescript
// ConversationStore.ts
initCache(userId: string) {
    const cacheAccess = Date.now() - this._cacheTimestamp
    if (!this._cacheVersion.startsWith(userId) || cacheAccess > 5 * 60 * 1000) {
        this.conversationMap = {}
        // ...
        return false
    }
    return true
}
```

两个 Store 的 `initCache` 方法使用 5 分钟过期策略来判断是否使用缓存。但存在以下问题：

1. `_cacheTimestamp` 仅在 `initCache` 时更新，正常使用期间不会刷新
2. 用户在 5 分钟内退出再登录会使用旧缓存，但期间的消息变更不会被反映
3. `conversationMap` 使用 `Record<string, Conversation>` 结构，序列化到 `localStorage` 可能受 5MB 容量限制

**优化建议**：
- 缓存过期策略应结合数据版本号或服务端推送的变更标识
- 考虑使用 IndexedDB 替代 localStorage，解决容量限制
- 增加缓存完整性校验

### E. 性能优化建议

| 优化项 | 当前状态 | 建议 |
|-------|---------|------|
| 消息列表渲染 | `MessageStore` 使用 `unshift` 在头部插入消息 | 大量消息时 `unshift` 性能较差（O(n)），考虑使用虚拟列表 + 尾部追加 |

# 未读消息、提示音与免打扰

## 启用前的操作

本次同时修改 Electron 和 Java 的 `im-chat`，按用户要求没有运行测试、构建、启动服务或执行数据库 SQL。

先在 IM 业务数据库执行一次：

```sql
ALTER TABLE conversation
    ADD COLUMN last_read_message_id BIGINT NOT NULL DEFAULT 0
    COMMENT '当前用户已读到的最大消息ID，防止MQ延迟入库后重复计未读'
    AFTER unread_count;
```

脚本位置：`E:\JavaProject\IM-SpringCloud\db\migrations\2026-10-27-conversation-read-cursor.sql`。若字段已存在，无需重复执行。随后重启 `im-chat`，完整重启 Electron；只热更新 Vue 不会加载新的主进程及 preload IPC。

## 行为

- 侧栏消息图标显示所有可见私聊/群聊的未读总数，包括免打扰会话。超过 99 显示 `99+`，悬停可看实际总数。
- 点击会话、打开独立聊天窗口或重新聚焦正在阅读的聊天时，清除该会话未读。聚焦阅读期间新消息立即按已读处理；后台、最小化或其他会话里的消息累加未读。
- 未读数为 0 时，右键显示“标为未读”，写入后端后计数至少为 1；存在未读时显示“标为已读”，沿用现有已读接口清零。再次打开菜单时按最新计数切换。
- 右键菜单和单聊/群聊资料面板中的免打扰开关都同步后端、SQLite 和各窗口；失败时提示错误，不显示虚假的成功状态。会话列表显示免打扰图标。
- 免打扰保留未读计数，但不响铃、不闪托盘。全局通知开关、声音开关、私聊/群聊开关及免打扰时段也参与提醒判断。
- 会话未读角标按数字内容收缩，定位在固定 50px 头像的右上角；0 时移除，超过 99 显示 `99+`。右侧时间与状态分两行排列，置顶、免打扰图标放在下行，避免与时间重叠。

## 应用内右上角提示卡片（2026-10-27）

好友上线等事件仍由 WS 推送，原事件总线只向其他窗口广播，没有在来源窗口派发；广播时还把 Vue 组件转换为 JSON，丢失渲染函数，造成提示卡片不显示。

事件总线现先在当前窗口派发事件。`addNotification` 保留原组件对象，只在本地显示，因为 WS 已向各窗口分发同一事件，避免再次跨窗口广播产生重复提示；帖子、账号、同步完成等可序列化业务事件继续通知其他窗口。提示容器卸载时取消监听并清理自动关闭计时器，避免重新登录后积累旧监听。

本轮未运行测试或构建。重启 Electron 后，使用另一账号上线，检查右上角出现卡片、5 秒后自动关闭、手动关闭正常；同时打开设置或独立聊天窗口，确认主界面每次只显示一条上线提示。

## 提示音修复

`resources/message-sound.mp3` 已移动到 `public/audios/sfx/message-sound.mp3`，删除安装包中独立复制旧资源的配置。Vite 会把 public 目录复制到 renderer 输出，界面统一通过相对 URL 加载提示音，兼容开发和安装后的路径。

此前没有保存通知设置时会直接跳过播放，设置页的 `notificationSettings` 也未接入主进程存取，导致声音设置实际没有持久化。本次接通存取并默认开启消息声音；主窗口允许消息音频自动播放，播放错误会输出明确日志。主进程只通知主窗口播放一次，同一条消息重复投递不重复提示，短时间连发有 400ms 的声音节流。

## 计数与前后端职责

桌面主进程接收 WS 后先按消息 ID 查重，一次性计算并写入 SQLite 的未读计数，再向所有窗口广播会话状态；各窗口不再各自累加。清零、手动标未读、免打扰变更也广播给其他窗口。登录后的会话列表会从已同步的 SQLite 刷新旧界面缓存。

后端接口：

| 接口 | 处理 |
| --- | --- |
| `PUT /conversation/isReaded/{conversationId}?maxMessageId=...` | 以已展示的最大消息 ID 推进已读游标；不传参数时兼容旧客户端，使用当前已入库最大 ID |
| `PUT /conversation/markUnread/{conversationId}` | 当前用户的会话未读数至少设为 1，返回实际计数 |
| `POST /conversation/updateMuteStatus?conversationId=...&isMute=0/1` | 校验状态与当前用户会话，再持久化免打扰 |

已读处理在事务内锁定当前用户的会话行，保留游标之后尚未读取的消息数。消息 MQ 入库时，只有消息 ID 大于接收者的已读游标才递增未读，避免“WS 已看到并清零，MQ 之后入库又加一”。群聊消息不再给发送者本人增加未读。同一个窗口的已读/手动未读请求按顺序提交。

没有修改消息正文、消息 ID 或收发协议，也没有重写历史记录。已读游标使用现有大整数消息 ID，客户端通过字符串传递，Java 使用 Long。

## 手动验收建议

本次结果为代码实现，尚未运行验证。建议在应用上述迁移并重启后检查：

1. 两个不同会话分别收到 2 条、3 条消息，侧栏显示 5；打开其中一个后变为另一个会话的计数，重新登录后保持正确。
2. 聚焦聊天时接收新消息不积累未读；切到别的会话、最小化后会积累；重新打开清零。独立窗口打开/关闭和切焦点时同样检查。
3. 无未读时右键显示“标为未读”，操作后至少为 1；存在未读时显示“标为已读”，操作后清零，重新打开菜单应切换。检查角标为 1、两位数、99+ 时均不拉伸，时间与免打扰、置顶图标不重叠。
4. 开启会话免打扰后接收消息，角标继续累加但无提示音/托盘闪动；取消免打扰后恢复声音。全局声音开关也应可关闭、保存和恢复。
5. 确认消息音由新的 public 路径加载；不保存过通知设置的账号也能响铃。批量消息、重复投递及两个窗口同时打开时，不重复计算同一条消息。

# 弱网下的在线状态同步修复

日期：2026-10-28。

涉及 Electron、`E:/JavaProject/IM-SpringCloud` 后端、`E:/FlutterProject/im_app` 三个项目。

## 已确认的问题

1. `MQMessagePublish` 和 `MQMessageListener` 在 Channel 不可写时直接跳过投递。上下线通知不属于离线消息，写缓冲区繁忙时会永久漏掉这次通知。
2. `ChannelManageUtil.removeChannel` 按用户 ID 无条件删除映射；旧连接迟到的关闭回调会删除新连接。退出处理也会无条件删除 Redis 路由、在线状态并发出离线通知。
3. Electron 原来每 60 秒单向发送心跳，没有回包检测；连接失效时可能长时间保持已连接状态，且三次重连失败后会退出程序。
4. App 自动登录使用刷新凭证接口，不经过账号登录时的好友 ID 缓存初始化。该缓存有效期仅两分钟，过期后会影响通知接收者查询及在线好友交集查询。全量好友同步原来没有恢复这份缓存。
5. Electron 收到上线通知时，如果好友资料尚未加载，会访问不存在的联系人记录并报错。

## 修改后的行为

- 缓冲区繁忙时，上下线通知仍写入活跃连接的发送队列；其他业务消息的处理规则保持原样。
- 本地移除连接时比较 Channel 实例。Redis 登记增加连接 ID，使用 Lua 原子登记和按连接 ID 清理。旧连接不能删除新会话的在线状态，也不会产生错误的离线通知。
- 心跳与在线列表分离：类型 `0` 心跳只返回类型 `0` 轻量确认，并续期现有缓存，不查询好友在线交集。在线列表使用独立的类型 `19` 请求、类型 `10` 响应。
- Electron 和 App 每 30 秒发送一次心跳；连续 90 秒未收到有效消息则断开并重连。心跳确认不广播到页面，也不触发 App 的业务状态或缓存更新。Electron 采用有上限的重试间隔持续恢复，最长间隔 30 秒，并忽略旧连接的回调。
- 取消握手阶段自动发送在线列表，改由客户端在准备就绪后明确请求，避免与初始化请求重复。Electron 在页面监听就绪、重连及窗口恢复焦点时请求；App 在联系人同步完成后请求，恢复前台的同步复用同一入口。两端合并尚未完成的在线列表请求，不定时拉取完整列表。收到完整列表后覆盖旧在线状态，包括空列表。
- 全量好友同步从已经查询出的完整好友数据重建 Redis 好友 ID 集合；空列表清除旧集合。App 自动登录后也能恢复通知接收者缓存。
- App 断线时清空内存中的在线集合；Electron 允许先收到上线通知、再加载好友资料，并统一在线事件中的 ID 字符串格式。

## 验证

- Electron：在线快照和连接恢复的 12 个定向子用例通过。覆盖空列表、通知早到、延迟回包、连接假活、超过三次重试、旧回调、页面就绪后的补取、请求合并，以及多次心跳不重复拉取在线列表。
- 服务端：本轮 `PresenceDeliveryTest` 9 项通过，Maven 编译及测试成功。其中验证普通心跳只回复类型 `0` 且不查询好友集合；独立在线请求仍返回当前列表及空列表。此前 `FriendPresenceCacheTest` 2 项通过。
- 隔离 Redis 实例：验证同节点、跨节点旧连接清理保护，当前连接正常清理及重复清理；另外验证好友 ID 替换、有效期恢复、空好友列表清理。未修改运行中 Redis 的数据。
- App：本轮 16 项相关测试通过，包括实际本机 WebSocket 区分心跳与在线列表请求、250 毫秒延迟回包、上下线帧、断开后的自动重连、心跳不转发到业务层、消息卡片的关闭与跳转、窄屏布局等。`flutter analyze --no-pub` 通过。
- Electron 本次文件 ESLint 无错误，有两个原有未使用导入警告。
- 全量 Node 测试仍有一个既有失败文件：`messageCache.test.cjs` 的组件隔离环境缺少 `emitter`。该测试、`ChatBase.vue`、`MessageStore.ts` 本次均未修改。
- 全项目 Vue 类型检查仍被 `ChatBase.vue:765`、`:810` 两处既有 `data:initialized` 回调类型错误阻塞。

上述验证不等于真实账号在远程弱网及真实 Redis、RabbitMQ、Netty 集群下的端到端验收。尚未替用户重启运行中的服务或更新手机安装包。

## 加载改动

本轮协议调整需要同时加载新版 `im-server`、Electron 和 App，客户端需支持类型 `19` 在线列表请求及类型 `0` 心跳确认。此前的好友缓存修复涉及 `im-social`，首次加载那部分修复时也需要更新该服务。

正常收到类型 `9`、`11` 上下线事件时即时更新；登录、重连和恢复前台时通过完整列表校准。网络直接中断时，对方离线的确认仍受服务端现有 90 秒读空闲检测及网络恢复时间影响。
